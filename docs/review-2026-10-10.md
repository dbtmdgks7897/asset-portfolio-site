# My Asset Manager — review (2026-10-10)

Repo: `dbtmdgks7897/asset-portfolio-site` (cloned 2026-10-10, HEAD `1ef74e0 "v2 최종"`, 76 commits, 2023-07-28 → 2023-08-20).
Scope: investigation only. No product code was changed. Everything that was built or run was run from a copy in a scratch directory, not from this folder.

How it was verified:

- Backend built with Temurin JDK 17.0.20 and the repo's Gradle 8.2.1 wrapper. Front end built with Node 18.20.8 (and Node 25 as a cross-check).
- **No Docker and no MariaDB on this machine.** The app was booted against **H2 in MariaDB compatibility mode**, using a patched copy of `data.sql` kept outside the repo, via command-line overrides only. The patch removed the duplicate admin insert, added a missing `;`, converted double-quoted literals for H2, and added a demo admin plus a demo portfolio.
- Live API calls were made with curl. Screenshots came from headless Chrome (Playwright) driving the running jar.
- Where a finding depends on H2 rather than on the code, it is marked **(H2-only)**.
- External services were probed **without credentials**. No secret found in git history was used.

## 0. Verdict in one paragraph

The app is a **real, working 3-week full-stack prototype**. When it boots, the UI matches the 2023 mockups: portfolio pies, an analysis dashboard, crypto detail with live Upbit prices, a board with comments, and admin pages.

It is not deployable as-is:

- The committed `data.sql` stops a clean boot.
- There are several authorization holes. Anyone can edit any board post without logging in. Any logged-in user can read or modify other users' portfolios.
- A `Long !=` comparison locks every user with id > 127 out of their own portfolio.
- The analysis math is wrong, and a percentage is shown ×100 too small.
- 2 of the 5 market-data sources are dead or need keys.
- Spring Boot 3.1 has been out of OSS support since 2024.

**Recommendation:** keep it as an **archived 2023 snapshot**. Give it good screenshots, the existing YouTube demos, and an honest README. A "revive and deploy" would be closer to a rewrite of the asset half than a polish pass. Details are in §6.

## 1. Spec as implemented

### 1.1 Architecture

- **Back end:** Spring Boot 3.1.2, Java 17, Spring Security 6.1 (session + form login), JPA/Hibernate 6.2, MariaDB driver, springdoc 2.1 (Swagger UI at `/api-docs`), Caffeine cache, `@Scheduled` price updater.
  - Packages: `domain/<feature>/{controller,dto,service}` and `model/<aggregate>/{entity,repository}`.
  - Every controller returns `ResponseEntity<ResponseDTO{code,message,data}>`.
- **Front end:** Vue 3.3 (Options API), vue-router 4, axios, vue-chartjs/Chart.js 4, SCSS, Bootstrap 5.3 and Bootstrap Icons (from CDN).
  - `npm run build` writes into `../src/main/resources/static`, so the jar serves the SPA.
  - SPA deep links work through a hack: `RootController` maps `/error` → `static/index.html`. That is why every deep link is served with **HTTP 404** status (confirmed).
- **Schema:** Hibernate `ddl-auto: create-drop`, plus `sql/data.sql` seed (102 mock users, 100 posts, 100 comments, roles, asset types). `schema.sql` exists but is not wired.

### 1.4 Where the code departs from the Notion plan

- **Asset main** was planned with KOSPI / S&P 500 indexes and commodities (gold/silver). Only the asset types `원자재_금/은` exist; there is no page and no data source.
- **Analysis** was planned per holding: profit, rate, weight, dividends. What exists is per asset class plus a total, with the math bugs below. Dividend columns exist (`dividend_month/amount`, DTO fields misspelled `divedendMonth`/`divendedAmount`), but no UI ever sets them.
- **Real-time quotes:** the domestic detail page opens a KIS WebSocket. It uses `ws://ops.koreainvestment.com:21000/tryitout/…`, which is the sandbox path, not TLS, and would be blocked as mixed content on any HTTPS host.
- **OAuth2 / "app deployment"** were noted as candidates and never done.
- **Notion "learned" item "check suspension in UserDetailsService":** suspension is checked in `CustomUserDetails.isAccountNonLocked()`, which works. The equivalent **deletion check is inverted**: a withdrawn account can still log in (confirmed).
- **Commit 1 TODO memo** (`ㅇㅇㅇㅇㅇㅇㅇㅇㅇㅇㅇxt.txt` at repo root) lists "hide hidden posts from the list" and "router guard". Neither was done: hidden posts still show in the public list, and the router guard is commented out.

## 3. Performance

Measured on H2 with the seed data (100 posts, 100 comments, 6 assets), counting Hibernate statements per request:

| Request | SQL statements | Note |
|---|---|---|
| `GET /board` | **166** | N+1. `BoardEntity.userEntity` is EAGER, `BoardEntity.commentEntityList` is **EAGER** (comments are loaded for every post in the list), `CommentEntity.userEntity` is EAGER. Also no pagination: all rows, 18 KB, sorted and paged in the browser. |
| `GET /portfolio` | 6 (1 portfolio) | Grows as 1 + N(portfolios) × (details + asset + type). `PortfolioEntity.portfolioDetailEntityList` is EAGER, and the service then re-queries details per portfolio anyway. |
| `GET /portfolio/analyze/{id}` | 7 | `ManyToOne` default EAGER on detail → asset → asset_type. Fine at this size, N+1 at scale. |
| `GET /transaction` | 7 | same pattern |
| every authenticated call | +1 | Each service re-loads the user with `findByEmail(principal)`, often 2–4 times per request (board/comment services call it repeatedly in one method). |

Fixes, in order of value:

1. Make every `@ManyToOne` and `@OneToMany` LAZY. Remove `BoardEntity.commentEntityList` EAGER; the list DTO only needs a comment count, so use `size()` via `@Formula` or a `COUNT` subquery. Use fetch joins / `@EntityGraph` for list queries.
2. Add server-side pagination (`Pageable`) to the board, admin board, and admin user lists.
3. Replace the `ORDER BY CASE …` queries with `Sort` built from a whitelist of columns.
4. Add indexes:
   - `board(deleted_at, created_at)`, `board(view_count)`, `board(recommend_count)`
   - `comment(board_idx, deleted_at, created_at)`
   - `portfolio(user_idx, deleted_at)`
   - UNIQUE `portfolio_detail(portfolio_idx, asset_idx)`
   - UNIQUE `bookmark(user_idx, asset_idx)`
   - `transaction(portfolio_idx, transaction_date)`

   Fix the recommend/report unique bug at the same time. The search uses `LIKE '%x%'`, which cannot use B-tree indexes; acceptable at this scale.
5. Read the user once per request from `CustomUserDetails` (it already holds `idx`) instead of `findByEmail`.

External API call patterns:

- `new RestTemplate()` is created per call in 3 services; the configured bean is used only in 2. There are no timeouts, so a hung upstream blocks a Tomcat thread indefinitely.
- KIS access token: cached (Caffeine), but the custom `CacheManager` (60 min TTL) silently overrides the YAML spec (1440 min). KIS tokens last 24 h and issuance is rate-limited, so a 60-minute refetch is wasteful but harmless.
- Prices are **not cached between users**. Every detail-page view calls Upbit/KIS directly. The scheduler updates DB prices only every 12 h, and the loop stops at the first failure. Better: per-source try/catch, a short TTL cache (10–60 s) per ticker, and batching (Upbit `ticker?markets=a,b,c` takes many markets in one call).
- Browser-side calls: Upbit `market/all` (67 KB, ~700 rows rendered in one table, refetched whenever the search box is cleared), fawazahmed0 (dead), AlphaVantage (key exposed). Moving these behind the backend with a cache fixes the key leak, CORS fragility, and the rate limits in one move.

Front-end weight (production build plus CDN, transfer sizes):

| Asset | Size | Note |
|---|---|---|
| `main-bg.jpg` (landing hero) | **9.9 MB**, 5760×3840 | The landing page's LCP. A 1920-wide JPEG q75 is 250 KB; WebP q75 is **55 KB** (−99.5%). It is committed twice (`front/src/assets` and `static/img`). |
| `chunk-vendors.js` | 330 KB / 115 KB gz | Bundles vue, vue-router, axios, chart.js, vue-chartjs. |

| Unused npm deps | `vuex`, `bootstrap-vue` (Vue 2 only), `sockjs-client`, `stompjs`, `net-browserify`, `volar-service-vetur@latest` (an editor plugin in `dependencies`), and `aos`/`bootstrap`/`bootstrap-icons` npm copies (loaded from CDN instead) | Remove. |

Vue rendering:

- There are no `v-html` uses (good).
- Layout is sized almost entirely in `vw` units (font sizes like `1vw`, `3vw`, buttons `6vw × 5vw`), with only 9 `@media` rules in the whole app. This is the root cause of the mobile breakage below.
- 172 `alert()` calls act as the error and confirmation UI.
- 41 `console.log` calls are left in.
- Error handling treats any 500 as "not logged in" and redirects to `/login`.

## 4. Design and UX

What works: a consistent visual system. It uses a dark left sidebar, white content cards on a grey canvas, a purple accent rule under H1s, and the SUITE font. Charts, analysis tiles, and the crypto detail page are readable on desktop and match the 2023 mockups.

Issues, roughly by visibility:

1. **Mobile is broken.**
   - At 390 px the sidebar collapses to a grey strip with unreadable 4 px labels.
   - Pie cards overflow horizontally, and headings wrap per character ("보유 자산 리스트" at ~60 px).
   - Tables are wider than the viewport.
   - The vw-based type scale makes text either tiny or huge.
2. **Placeholder copy shipped.**
   - "Footer" is the entire footer on every page.
   - "로그인 하소" (sidebar CTA).
   - "님 누구세요?", "게시물?이 없습니다?", "내 정보인데?" and "즐겨찾기 리스트~" appear as API messages and Swagger text.
   - "데모 포트폴리오 **포트폴리오**": the title doubles the word.
   - "선택창" is used as the back-link label.
3. **Landing page** is a 10 MB stock photo with the logo and no copy, and its only button leads to the **board**, not the product. On first visit there is no explanation of what the app does.
4. **Empty, error, and loading states.**
   - There are no skeletons or spinners. Pages render empty frames until data arrives: the bitcoin detail without a name shows only "(KRW-BTC)".
   - A null price renders as a bare "원".
   - FX shows empty dropdowns when the API is down.
   - Errors are `alert()` boxes, often "로그인 해주세요" for unrelated failures.
   - `/mypage/info` is a blank grey page.
5. **Information design.**
   - Portfolio pies show **purchase cost**, not current value, so they don't reflect the portfolio's actual allocation.
   - The analysis tiles show a ratio with a "%" sign (0.15 % means 15%).
   - Analysis labels use the four-icon pattern (money/chart/$/₿) with 16 identical tiles and no hierarchy. The total row should dominate.
   - Transaction "총 거래액" shows profit.
   - Date formats are inconsistent: `10/04/13 01:29`, `2023-06-16T01:03:44`, `23/08/19`.
6. **Navigation and accessibility.**
   - Sidebar items, table rows, and buttons are `<li @click>` / `<a>` without `href`. They are not focusable and do not work with a keyboard.
   - Only 6 `<img>` (all with `alt`) — the logo has `alt=""`, which is OK for decoration.
   - Icon-only buttons (comment report/recommend, sidebar toggle) have no accessible name.
   - Colour-only meaning: red/blue up/down with no sign glyph on some tiles.
   - Small (~13 px) purple outline buttons and the light-grey labels on the analysis tiles look borderline for AA contrast (not measured).
   - `<html lang="">`. The page `<title>` is the Vue CLI default "front".
7. **Consistency.**
   - Primary actions use at least four styles: purple outline, red outline, black outline, text-only "구매/판매".
   - Card borders alternate between 1 px black and shadow-only.
   - The sidebar height is fixed to the viewport, so it ends mid-page on long pages (visible on board detail and portfolio detail).
8. **Deep links.** `/asset/bitcoin/KRW-BTC` without `?bitcoinName=` renders empty. Every SPA URL returns HTTP 404 (it works in browsers, but crawlers and link-preview bots treat it as missing).

## 5. Code quality and security

### 5.1 Authorization / authentication (all confirmed against the running app unless noted)

| # | Severity | Finding | Where |
|---|---|---|---|
| A1 | **Critical** | **Anyone, without logging in, can edit any board post.** `PUT /api/v1/board/{id}/update` takes no principal and no owner check, and the security config `permitAll()`s everything except `/admin/**` and `/mypage/**`. Confirmed: an anonymous PUT changed post 3. | `BoardControllerApiV1.updateBoardData`, `BoardServiceApiV1.updateBoardData`, `SecurityConfig` |
| A2 | **High** | **IDOR on portfolios.** `portfolio/detail/{id}/chart` and `portfolio/analyze/{id}` return any user's holdings (confirmed: read user 101's portfolio as user 900). `asset/purchase`, `asset/sell`, and `portfolio/detail/{id}` (delete holding) never check that the portfolio belongs to the caller (by inspection), so anyone can write into or wipe someone else's portfolio. | `AnalyzeServiceApiV1`, `PortfolioDetailServiceApiV1`, `AssetServiceApiV1` |
| A3 | **High (functional)** | **`Long` compared with `!=`.** `userEntity.getIdx() != portfolioEntity.getUserEntity().getIdx()` compares object references. Java caches `Long` only for −128…127, so **every user with id ≥ 128 is denied access to their own portfolio detail, transactions, and portfolio delete** (confirmed with id 900). The same pattern is used for board and comment delete/update ownership. The seed has 102 users, so the 26th new sign-up hits it. | `PortfolioServiceApiV1`, `PortfolioDetailServiceApiV1`, `TransactionServiceApiV1`, `BoardServiceApiV1`, `CommentServiceApiV1` |
| A4 | High | **Withdrawn accounts can still log in.** `isAccountNonExpired()` returns `true` once `now > deletedAt`, which is immediately after withdrawal. The logic is inverted. Confirmed: delete account → login succeeds. | `CustomUserDetails` |
| A5 | High | **No input validation runs at all.** `hibernate-validator` (`spring-boot-starter-validation`) is not on the classpath, so every `@Valid`, `@NotBlank`, and `@Pattern` is a no-op. Confirmed: sign-up with `email: "notanemail"`, `password: ""` succeeds. The phone regexes are also malformed JS-style strings (`"/^\\d{3}-…$/\r\n"`) that would reject every phone if validation were ever enabled. | `build.gradle`, `ReqJoinDTO`, `UserEntity` |
| A6 | Medium | CSRF disabled while using cookie sessions. Mitigated somewhat by JSON bodies and browser SameSite=Lax defaults; the multipart `mypage/info/update` and form login/logout are still exposed. | `SecurityConfig` |
| A7 | Medium | **Third-party API key served to any logged-in user** (`GET asset/stock/overseas/apikey` returns the AlphaVantage key). | `OverseasServiceApiV1` |
| A8 | Medium | Unauthenticated calls to user-scoped endpoints throw NPEs (`customUserDetails` null). The global handler doesn't catch them, so they become a 500 forwarded to `index.html`. | all services |

### 5.3 Correctness bugs (beyond security)

- **Analysis math** (`AnalyzeServiceApiV1`):
  - `totalSummaries[2]` adds the *running* per-class profit on every row, which double counts. In the demo: reported total profit 18.78 M vs. true 11.68 M.
  - `totalSummaries[3]` sums per-row rates: 6.44 reported vs. 1.01 true.
  - Rates are ratios but are displayed with "%" (×100 missing).
  - Divide by zero if a class has a total purchase of 0.
  - The 2023 mockup already shows this: "총 수익률 0.27 %" where the true rate was ~8.5%.
- **Sell cost basis** (`postPortfolioDetailSell`): subtracts the *sell proceeds* from the total purchase cost instead of `avgPrice × soldQty`. The average cost drifts after every partial sale and can go negative.
- **Buy/sell are not `@Transactional`** (`AssetServiceApiV1.purchaseAsset/sellAsset`). A failure halfway leaves a detail row without a transaction row or the reverse. Totals and profit are computed on the client and trusted.
- **Recommend/report unique constraints** (§1.3) allow only one recommend per user, ever.
- `board.content` and `comment.content` are VARCHAR(255), so a post longer than 255 characters gives a 500.
- Board search (`findByNameContainingOrContentContainingOrUserEntity_NameContainingAndDeletedAtIsNull`) parses as `A OR B OR (C AND deletedAt IS NULL)`, so deleted posts appear in search. Hidden posts (`is_hided`) are never filtered in the public list.
- The audit log `rowId` is often `repository.count()` instead of the new row's id. `created_at` is never set.
- Portfolio name uniqueness is checked across **all users**.
- The admin user list crashes on a null `created_at`.
- `ddl-auto: create-drop` **drops every table on every shutdown**. Any deployment would lose all user data on restart.

### Frank opinion

**Keep it as an archived 2023 snapshot with good screenshots.** Do (a1)–(a4), which is about half a day, and stop.
